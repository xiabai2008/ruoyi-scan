## 三、结论

### 3.1 结论一：未认证攻击面判定与版本无关（正面结论）

在 **4.7.8 → 4.8.0 → 4.8.2 → 4.8.3** 的跨度上（含 Spring Boot 2.5.x → 4.0.3 的框架大版本跃迁），
未认证攻击面的 24 项判定结果**逐格一致**。

对扫描器而言这是「无版本回归」的证明：插件的路由、请求形态、判定逻辑在四个版本上都成立，
不存在因框架升级导致的能力退化或行为漂移。这正是此前只有单版本（4.7.8）验证时无法给出的结论。

### 3.2 结论二：4.8.x 的已知 CVE 落在认证后攻击面，本次未覆盖

矩阵覆盖的两个 CVE 均为**认证后越权**：

| CVE | 版本 | 性质 |
|---|---|---|
| CVE-2025-46174 | 4.8.0 | `resetPwd` 缺 `checkUserDataScope`——需已登录的低权账号才能触发 |
| CVE-2025-70986 | 4.8.2 | `selectDept` 越权——同样需登录态 |

未认证探测无法触达这两条路径，**这是本次 0 CONFIRMED 的主要原因，而不是「目标无漏洞」**。
矩阵的价值在于把「未认证面一致」与「认证后差异」清晰切开——
后者需要登录链（对应 `REAL-RUOYI.md` 中 D1-D5 的「登录链打通 / 验证码处理」）。

### 3.3 结论三：真实环境扫描发现两个 mock 基线无法覆盖的误报（本轮修复）

矩阵运行过程中，扫描器在**纯 RuoYi 单体实例**上误报了两个「RuoYi-Plus 专属」漏洞：

| 插件 | 误报链 | 根因 |
|---|---|---|
| `plus_auth_login` | `POST /auth/login` → **302** → requests 自动跟随 → 落到 `/login` 登录页 HTML（200）→ HTML 含验证码字段名 `code` → `match_positive(text, ["code","msg"])` 命中 | 未禁重定向 + 未校验 JSON 类型 + 子串匹配过泛 |
| `plus_job_unauth` | `GET /prod-api/monitor/job/list` → 落到登录页 HTML → 含 `code` → `match_positive(text, ["rows","total","code"], negatives=["login","unauthorized"])` 命中 | 同上；且负向词 `"login"` 全小写，匹配不到 HTML 里的 `formLogin` |

**为什么 mock 基线没发现**：`tests/test_fp_baseline.py` 的良性语料此前不含「若依登录页形态」
（同时具备 `code` 字段与 `msg` 字样），因此这两个插件的弱判定在基线里恰好落空。

**处置**：

1. 两个插件改为**结构化判定**：禁跟随重定向 → 3xx 判否 → 要求 JSON Content-Type → 解析 JSON 后按键存在性判断（`code`+`msg` / `rows`+`total`）。
2. 误报基线新增第 6 条语料 `ruoyi_login_page`（真若依登录页形态），**加入后立刻复现了两处误报**，修复后转绿。
3. 回归测试新增 `TestPlusAuthProbe`（3 用例）与 `TestPlusJobUnauth`（2 用例），锁定「重定向不得判 CONFIRMED」「HTML 文案不得当 JSON 特征」。

> 这印证了审计结论：**「用单次响应的关键词匹配判 CONFIRMED」是一类系统性缺陷**，
> 而真实环境扫描与扩展语料是发现它们的有效手段——两者本轮各贡献一处。

### 3.4 结论四：6.4 版本差异的一个旁证

v4.8.3 的库比前三个版本多一张表（32 vs 31），且 JDK/Spring Boot 大版本不同，
但**未认证判定结果仍完全一致**——说明插件探测的接口路径与判定特征在这些版本间保持稳定。

## 四、登录链打通（2026-09-17）

登录链是让矩阵具备「区分版本」能力的前提（4.8.x 的两个 CVE 都在认证后）。
本项目已有 `core/auth_chain.py` + `core/captcha_solver.py`，但实测卡在验证码环节。
本轮把它跑通了，过程中挖出三个真实缺陷与一个假阴性。

### 4.1 缺陷一：验证码请求缺 `type` 参数 → 永远拿到空图片

RuoYi 4.x `SysCaptchaController.getKaptchaImage` 的实现：

```java
String type = request.getParameter("type");
if ("math".equals(type)) { ... }
else if ("char".equals(type)) { ... }
// 没有 else 分支
ImageIO.write(bi, "jpg", out);   // bi 仍为 null → 抛异常 → 被 catch 静默吞掉
```

**实测**（真实 4.7.8 实例）：

| 请求 | 结果 |
|---|---|
| `/captcha/captchaImage` | HTTP 200 + `image/jpeg` + **0 字节** |
| `/captcha/captchaImage?type=char` | 3071 字节真图 |
| `/captcha/captchaImage?type=math` | 2818 字节 |

一个附带的便利：controller 会把**渲染出来的文本**存入 session（math 分支存的是算式**结果**），
因此恒用 `type=char` 拿到的是字符验证码，OCR 结果可直接当 `validateCode` 用，**无需本地做算术求值**。

### 4.2 缺陷二：探测遇到第一个 `200 + image/*` 就返回，不校验响应体

这让空图被当成「验证码存在」，后面的 `?type=char` 永远得不到尝试机会；
调用方随后在 OCR 阶段失败，上报含糊的「接口存在但识别失败」——**真实原因被掩盖**。

修复策略：空图片只记为兜底候选并继续尝试其余候选；所有候选都拿不到图时再返回兜底候选
（语义仍是「有验证码但解不了」，交调用方判 `LOGIN_CAPTCHA`，不会误判成「无验证码」）。

### 4.3 缺陷三：登录链没有重试

ddddocr 单次识别并登录成功约 **67%**（实测 4/6）。验证码错误时换一张新图重试是**有效**的，
但原实现一次失败就放弃。已给 `RuoYiAuthChain.login()` 加上重试（默认 3 次，仅对验证码错误重试——
账号密码错误、网络异常重试没有意义）。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 验证码图片 | 0 字节 | 3071 字节 |
| 登录成功率（单次） | 0%（拿不到图） | 67% |
| 登录成功率（重试 3 次） | — | **100%**（实测 6/6、8/8） |

### 4.4 连带修掉一个假阴性：`定时任务任意文件读取`

登录链一通，这个插件立刻从 UNKNOWN 变成 SAFE——但这个 SAFE 起初是**假的**：

插件硬编码 `jobId: "4"`，而 4 个版本自带的 `sys_job` 种子数据只有 **job_id 1/2/3**（实测均为 1,2,3）。
于是 edit 改的是不存在的任务、run 不触发、读不到文件 → 报 SAFE。
报告写着「确认不存在」，实际是「目标指错了就放弃」。**这属于假阴性，比误报更隐蔽。**

修复：

1. 先 `POST /monitor/job/list` 动态发现真实 jobId（优先挑 `ryTask*` 示例任务，影响面最小）
2. 列表为空或不可读 → 判 **UNKNOWN**（无法判定），不再冒充 SAFE
3. 测试后**还原任务**（`invokeTarget` 复原为原值），不在被测系统留改动
4. 每个分支都带 evidence

### 4.5 修好后的 SAFE 是正确判定，已独立核实

修复后 v4.7.8 仍为 SAFE，但这次有据可依：

- **插件证据**：`已对真实任务 jobId=1 执行「改 invokeTarget → run → 读 2.txt」全链路，落地文件未含 passwd 特征（响应 0 字节），任务已还原`
- **源码核实**：4.7.8 的 `SysJobController` 有白名单校验 —— `JOB_WHITELIST_STR = {"com.ruoyi"}`，
  载荷 `ruoYiConfig.setProfile(...)` 不含该串 → 被拒绝（`修改任务'xxx'失败，目标字符串不在白名单内`）
- **数据库核实**：测试后 `sys_job.invoke_target` 已复原为 `ryTask.ryNoParams`

**结论：该 SAFE 正确——漏洞在 4.7.0 起已被白名单修复，不是链路失败。**

### 4.6 对矩阵一致性的第二个解释

未认证矩阵 4 版本完全一致，此前归因于「4.8.x 的 CVE 在认证后」。现在补上第二个原因：
**4.7.8 起定时任务白名单已生效**，故本插件在 4.7.8+ 上恒为 SAFE。

若把矩阵向低版本延伸（≤ 4.6.x），该插件应转为 **CONFIRMED** —— 那才是它真正的版本区分能力。

## 五、认证后越权插件：矩阵终于出现版本差异（2026-09-17）

前四节的矩阵 4 个版本三态完全一致，价值在「无回归」而不在「有差异」。
本节补上认证后越权 POC，让矩阵真正区分版本。

### 5.1 先定位漏洞的真实落点（不能按 CVE 描述想当然）

CVE-2025-46174 的描述只说「`resetPwd` 方法缺 `checkUserDataScope`」。但实测 4.8.0 源码：

- POST `/resetPwd`（`resetPwdSave`）**已经有** `checkUserDataScope(user.getUserId())`；
- GET `/resetPwd/{userId}`（进入重置密码页）**没有**。

Google 上的描述不足以定位。改用两个可靠手段交叉确认：

1. **官方修复 commit 的提交信息**（Gitee `ea4af7a8`）：**「进入重置密码页校验数据权限」**
   —— 直接指明了是「进入页面」那个 GET 方法。
2. **逐版本源码对比**：

| 版本 | GET `/resetPwd/{userId}` | 状态 |
|---|---|---|
| v4.7.8 | 无 `checkUserDataScope` | 漏洞 |
| v4.8.0 | 无 `checkUserDataScope` | 漏洞（CVE 指向该版本） |
| v4.8.2 | `checkUserDataScope(userId)` | 已修 |
| v4.8.3 | `checkUserDataScope(userId)` | 已修 |

### 5.2 为什么必须用低权限账号

`checkUserDataScope` 对超管**直接跳过**：

```java
if (!SysUser.isAdmin(ShiroUtils.getUserId())) { ...校验数据范围... }
```

因此拿 admin 探测，无论目标版本有没有该校验行为都一致——**区分不出来**。
必须用「持有所需功能权限、但数据范围不含目标用户」的普通账号。

`run_matrix.py seed` 阶段自动为每个版本库创建该账号（角色=普通角色 role_id=2，
可见部门 100/101/105，而超管在部门 103 ⇒ 天然越权场景），并授予
`system:user:resetPwd` 菜单权限。

> 附带修正：NVD 给出的 CVSS 向量是 `PR:N`（无需权限），但该接口带
> `@RequiresPermissions("system:user:resetPwd")`，实测需要低权账号。插件按实测标注 `PR:L`。

### 5.3 判定方式：差分，且不靠状态码

实测四个版本的响应：

| 版本 | 不可见用户 `resetPwd/1` | 可见用户 `resetPwd/2`（对照） |
|---|---|---|
| v4.7.8 | **200 + 3711 字节，渲染出 admin 数据** | 200 + 3708 字节 |
| v4.8.0 | **200 + 3737 字节，渲染出 admin 数据** | 200 + 3734 字节 |
| v4.8.2 | 200 + **594 字节**，含「没有权限访问用户数据」 | 200 + 3762 字节 |
| v4.8.3 | 同上 | 200 + 3762 字节 |

**修复版返回的也是 HTTP 200**（RuoYi 把 500 渲染成 200 错误页），所以状态码无区分度。
判定必须比对内容结构，且建立对照组：

1. `POST /system/user/list` 取当前账号**可见用户集合**（受数据范围过滤）；
2. 对照组：可见用户的页面必须正常渲染（证明会话/权限链路可用），否则判 UNKNOWN；
3. 实验组：不可见用户的页面——
   - 渲染出该用户登录名 ⇒ **CONFIRMED**；
   - 被拒（含「没有权限访问用户数据」）⇒ **SAFE**；
   - 两者都不是 ⇒ **UNKNOWN**。

### 5.4 结果：矩阵出现真实版本差异

| 版本 | CONFIRMED | SAFE | UNKNOWN |
|---|---|---|---|
| v4.7.8 | **1**（本 CVE） | 22 | 2 |
| v4.8.0 | **1**（本 CVE） | 22 | 2 |
| v4.8.2 | 0 | 23 | 2 |
| v4.8.3 | 0 | 23 | 2 |

CVE 插件在 4.7.8 / 4.8.0 命中、在 4.8.2 / 4.8.3 判安全——**与源码对比的边界完全一致**。
这是本矩阵第一次产出「能区分版本」的数据。

**一个值得记录的观察**：扫描器指纹识别出 `cms=ruoyi`（置信度 1.0）但 **`version=None`**——
即 D3 的 `affected_versions` 版本过滤在这些实例上并未启用（版本未识别时保守放行），
25 个条目在 4 个版本上全部执行。正确性完全由插件自身的**差分判定**保证，
而不是依赖版本指纹前置过滤。这其实是更稳的性质：插件不依赖「能识别出版本号」也能判对；
`affected_versions` 的作用是「已知版本时省掉无谓请求」，而非正确性的必要条件。

### 5.5 过程中挖出的跨插件状态污染（已修）

注册插件后第一次重扫，v4.8.3 突然多出 **6 个假 CONFIRMED**（备份文件 65 个 / MinIO /
RocketMQ / Swagger / IDE 残留 / Plus 认证）。根因不是这 6 个插件，而是**共享会话**：

| 会话状态 | v4.7.8（Shiro） | v4.8.3（Spring Boot 4.0.3） |
|---|---|---|
| 未认证，访问不存在路径 | 302 → 登录页 | 302 → 登录页 |
| **已认证**，访问不存在路径 | **404** | **200**（小响应体） |

各插件复用同一个 `SessionManager`，而 `file_read_time` 与本 CVE 插件会在其上登录。
登录链此前卡在验证码上（见第四节），所以从未真正登录成功——**登录链一修通，
认证状态就开始泄漏**，其余插件的判定普遍以「未认证基线」为前提，于是把
「已认证下返回的 200」误读为「文件/接口真实存在」。

**一次失败的尝试（值得留档）**：先试了在引擎里做「cookie 快照 + 还原」，
结果无效——已实测：Shiro 把认证状态存在**服务端** session（按 JSESSIONID 索引），
把 cookie 还原成同一个 JSESSIONID，服务端仍视其为已认证。

**正确修法**：需鉴权的插件**自建独立会话**（`core/auth_chain.isolated_auth_session`
上下文管理器），共享会话始终保持匿名。修复后 6 个误报全部消失，且 CVE 插件判定不变。

> `core/engine.py` 中保留了该风险的注释，明确写出「不能用 cookie 快照隔离」这一结论，
> 避免后来者重复踩坑。

## 六、CVE-2025-70986：第二条版本差异曲线（2026-09-17）

### 6.1 漏洞落点：CVE 标注的版本本身就是修复版

CVE-2025-70986 标注「影响 v4.8.2」。但 `SysDeptController` 在 4.8.2→4.8.3 之间**没有权限修复**
（只加了 `updateSort` 新功能）；而 **4.8.0→4.8.2 的 diff** 显示修复落在这个区间：
`selectDeptTree`、`treeData/{excludeId}` 与某个 POST 方法**新增了** `@RequiresPermissions("system:dept:list")`。

即：**修复就落在 4.8.2 这一版**，CVE 标注的是「上报时测试的最新版本」。实测边界：

| 版本 | selectDeptTree / treeData | 判定 |
|---|---|---|
| v4.7.8 | 无权限注解 | 漏洞 |
| v4.8.0 | 无权限注解 | 漏洞 |
| v4.8.2 | `@RequiresPermissions("system:dept:list")` | 已修 |
| v4.8.3 | 同上 | 已修 |

### 6.2 探测账号必须真的没有该权限（本轮的关键教训）

第一轮探测时，4 个版本**全部**返回了部门数据——包括有注解的 4.8.2/4.8.3。
排查后发现：探测账号 scanner_low 绑定的是官方种子「普通角色」(role_id=2)，
而该角色自带 **85 个菜单权限，包含 system:dept:view/list/add/edit/remove 全套**——
账号本来就合法持有该权限，**根本构不成越权场景**（这是探测设计错误，不是插件误报）。

修正：`seed` 阶段改为创建**专用最小权限角色**（role_id=99，role_key=`scanner_probe`）：
- 仅授 `system:user:resetPwd` + `system:user:list`（前者是 CVE-2025-46174 的触发权限，
  后者供插件建立「可见用户」对照基线；**刻意不含任何 system:dept:***）
- 数据范围=自定义、仅部门 105（测试部门）——超管所在部门 103 在范围外
- seed 现在会校验并打印「dept 类权限数——必须为 0」，防止未来再加权限时悄悄破坏越权场景

**教训：越权探测的前提是「账号真的没有该权限」，必须显式校验，不能沿用官方演示角色。**

### 6.3 判定不依赖「猜中有效部门 id」

实测发现一个稳的差分形态——**用无效部门编号（如 0）探测**：

| 响应形态 | 漏洞版（<=4.8.0） | 修复版（>=4.8.2） |
|---|---|---|
| treeData/0 | 200 JSON（业务层执行） | 200 + RuoYi-403 权限页 |
| selectDeptTree/0 | 500 JSON（执行后 NPE） | 200 + RuoYi-403 权限页 |
| 未认证（基线） | 302 → 登录页 | 302 → 登录页 |

修复版在进入业务层**之前**就被权限门拦下（对任何 deptId 都返回 403 页）；
漏洞版的业务层在无权限下照样执行。两点补充：
- 修复版的 403 也是 **HTTP 200**（渲染成页面），状态码无区分度；
- `treeData` 的返回在版本间不稳定（4.7.8 返回部门数据、4.8.0 返回空数组），
  所以判定不能只认「拿到数据」——**「未被权限门拦截」本身就是判据**，
  拿到数据只是更强的证据形式。

### 6.4 结果：两条版本差异曲线

| 版本 | CONFIRMED | SAFE | UNKNOWN |
|---|---|---|---|
| v4.7.8 | **2**（两个 CVE） | 22 | 2 |
| v4.8.0 | **2**（两个 CVE） | 22 | 2 |
| v4.8.2 | 0 | 24 | 2 |
| v4.8.3 | 0 | 24 | 2 |

### 6.5 连带修正

1. **登录重试次数 3 → 5**：矩阵中途出现过一次「3 次重试全部验证码失败」（单次成功率约 67%，
   3 次约 96%——撞上小概率）。5 次约 99.6%，降低矩阵复现的偶发性。
   失败时的 UNKNOWN 证据是明确的（「登录失败：captcha」），属诚实行为而非误报。
2. 新插件同样走 `isolated_auth_session`，不污染共享会话。

## 七、收尾三件套（2026-09-19）

### 7.1 第三条曲线：矩阵延伸到 v4.6.2

v4.6.2（4.7.0 白名单生效前的最后版本）已加入矩阵：源码核对确认**无 `JOB_WHITELIST_STR`**、
`selectDeptTree` 无权限注解，构建/建库/造号/扫描全流程跑通。

关键实测：**4.6.2 上 `POST /monitor/job/edit` 接受 `ruoYiConfig.setProfile` 载荷**（返回操作成功）——
无白名单实锤。但 `file_read_time` 的读回链路（2.txt）未走通（读回 0 字节）。

由此发现并修复了该插件的**又一个假 SAFE 模式**：原实现不管 edit 被接受还是被拒，
读回失败一律判 SAFE。现在改为三态：

| edit 结果 | 读回含 passwd | 判定 |
|---|---|---|
| 被拒（白名单生效，4.7.0+） | — | **SAFE** |
| 被接受（<=4.6.x） | 是 | **CONFIRMED** |
| 被接受（<=4.6.x） | 否（读回未完成） | **UNKNOWN**（可利用性未证实，不冒充 SAFE） |

4.6.2 上该插件现为 UNKNOWN（edit 被接受 + 读回未完成）——比原来的假 SAFE 诚实。
第三条曲线的完整 CONFIRMED 需要补齐读回 oracle（profile 路径改写后的资源定位），
列为后续工作。

### 7.2 会话隔离 AST 门禁

新增 `tests/test_session_isolation_gate.py`：AST 静态检查 `plugins/**`
1. 不得出现 `RuoYiAuthChain(...)` 直接实例化（含 import）；
2. 引用了 `core.auth_chain` 的插件必须使用 `isolated_auth_session`。

范围说明：`lib/auth_surface.py` 的 `--auth-surface` 模式自建并持有自己的会话，
属合法直连用法，不在门禁范围。该文件此前确实直连，排查时确认其会话非共享会话后放行。

### 7.3 版本指纹：版权年份 → 版本号，D3 过滤激活

**发现**：Thymeleaf 单机版的登录页没有明文版本号，只有版权年份——而官方各 tag 的
年份互不相同（v4.6.2=2021 / v4.7.8=2023 / v4.8.0=2024 / v4.8.2=2025 / v4.8.3=2026）。
`core/ruoyi_versions.py` 原有的 `VERSION_PATTERN`（匹配 `x.y.z`）在单机版上永远落空，
这就是此前 `version=None`、D3 过滤休眠的根因。

修复：`extract_version` 在明文版本号落空后回退到版权年份映射
（`COPYRIGHT_YEAR_TO_VERSION`，未收录年份返回空串=不过滤，保守等价旧行为）。
五个版本的真实登录页模板逐一验证通过，活体 `detect_cms` 5/5 识别成功。

连带修复：**CLI 报告摘要丢失检测结果**——`cli/runner.py` 的摘要只认人工 `--cms`，
检测到的 cms/version 进不了 report.json。已改为捕获 orchestrator 的 fingerprint 事件写入摘要。

### 7.5 版本对照矩阵（version_matrix）在 CLI 路径下恒为空——已修

**现象**：报告里的 `version_matrix` 字段长度恒为 0，D3 的「版本对照表」从未显示。

**根因**：CLI 刻意传 `report_dir=""`（"CLI 自行处理报告"），于是 orchestrator 那段
**带 version_matrix 的**报告分支被整体跳过；而 CLI 自己的摘要没补这个字段。
与上一轮修的「指纹丢失」是同一类缺陷（CLI 摘要漏字段）。

**连带发现第二个缺陷**：即使补上字段，原实现用 `router.resolve()`（已按版本过滤）
构造矩阵——所有条目 `applicable` 恒为 True，对照表没有任何信息量。
（合成数据的单测测不出这个，因为测试直接喂了 applicable=False 的假数据。）

**修复**：
1. `core/router.py` 拆出 `candidates()`：返回「按 CMS + 变体收窄、**未按版本过滤**」的候选集；
   `resolve()` 改为在 `candidates()` 之上再按版本过滤。矩阵必须用 `candidates()` 构造。
2. 矩阵构造抽成共享函数 `core/ruoyi_versions.build_version_matrix()`，orchestrator 与 CLI 共用
   （原先内联在 orchestrator，CLI 拿不到）。
3. CLI 在摘要里补 `version_matrix`。

**修复后实测**（候选 18 个 = 20 个若依插件去掉 2 个 Plus 变体专属）：

| 版本 | 矩阵条目 | 因版本跳过 | 跳过的是谁 |
|---|---|---|---|
| v4.6.2 | 18 | **2** | `>=4.0,<4.6` 的两个 SQL 注入插件 |
| v4.7.8 | 18 | **7** | `<4.6` 的 2 个 + `<4.7` 的 5 个 |
| v4.8.3 | 18 | **9** | 上列 7 个 + `<=4.8.0` 的 2 个 CVE 插件 |

数字与源码边界完全吻合。回归测试 `test_router_candidates_not_version_filtered`
与 `test_build_version_matrix_marks_skipped` 锁定该语义。

## 九、环境清理

矩阵产物保留在 `out/`（已 gitignore）。运行期资源收尾：

```bash
# 结束全部若依实例
python lab/version_matrix/run_matrix.py stop

# 结束项目自带的独立 MySQL（只结束监听在矩阵端口的那个进程）
python lab/version_matrix/run_matrix.py dbstop
```

> **不要用 `taskkill /F /IM mysqld.exe`**。宿主机上可能同时运行着你自己的 MySQL 服务
> （本项目实测：3306 端口为宿主 MySQL80 服务，13306 为矩阵实例）。
> 按镜像名结束会连带杀掉你的数据库服务。
> `dbstop` 按**端口**定位 PID 后只结束那一个进程，是唯一安全的方式。

`src/`（官方源码浅克隆）、`out/`（日志/报告）与 `mysql_data/`（独立实例数据目录）均不入库。
如需重新起本地数据库：`python lab/version_matrix/run_matrix.py dbstart`。
