# P 类缺陷清单：建靶场时预先发现（不计入盲测检出）

> 建立时间：2026-11-01（阶段 0.4 结束时）
> 用途：盲测 v2 阶段 2 对照时，把这些条目从「盲测检出」里排除。
> 分类口径在盲测**开始之前**定死，避免事后按有利方向归类。

## 什么是 P 类

P 类 = **在阶段 0.4 建 C4 靶场的过程中就暴露出来的缺陷**，不是盲测发现的。

它们的共同点是：**只有坚持「按真实产品形态建靶场、不照插件源码凑路径」，才会碰出来**。
如果按插件源码去搭靶场（把 `/rocketmq/` 这种路径做成真实可达），
这些缺陷永远不会暴露 —— 这正是「花架子」问题的根源。

## 清单

### P1 · `rocketmq_unauth` 探测路径全错

| 项 | 内容 |
|---|---|
| 发现方式 | 建 C4-3（真实 Spring Boot 复刻 rocketmq-console-ng）后第一次扫描 |
| 现象 | 真实控制台在 `GET /` 返回 200（含 `mqnamesrv`），插件判 **SAFE** |
| 根因 | 插件只探 `/rocketmq/`、`/dashboard/`、`/rocketmq-console-ng/` 三条「猜出来的前缀」，全部 404 |
| 真实形态 | rocketmq-console-ng 是**独立 Spring Boot Web 应用**，官方包 `context-path` 为空，控制台就挂在根路径 |
| 影响面 | 所有真实部署的 RocketMQ Dashboard |
| 修复 | `7fb3595` 候选加 `/` 置首位（靠 `rocketmq`/`mqnamesrv` 专有标识 + 排除 login 防误报） |
| 回归 | `tests/test_rocketmq_dashboard_paths.py` 8 条 |

### P2 · `minio_unauth` 探测路径全错（与 P1 同构）

| 项 | 内容 |
|---|---|
| 发现方式 | 建 C4-2（真实 S3 协议复刻）后第一次扫描 |
| 现象 | S3 根路径 `GET /` 返回 `<ListAllMyBucketsResult>`（3 个桶），插件判 **SAFE** |
| 根因 | 插件探 `/minio/` —— 那是**控制台登录页**，永远不含桶列表 |
| 真实形态 | 匿名桶列举走 **S3 协议根路径 `GET /`**；`/minio/` 是 Console SPA |
| 影响面 | 所有真实部署的 MinIO |
| 修复 | `a99bc46` 按序探 `/` 与 `/minio/`，任一命中即 CONFIRMED；两个都失败 → UNKNOWN |
| 附带修 | 正向特征从泛用 `"bucket"` 收紧成 S3 XML 结构（控制台出现 "bucket manager" 会误报） |
| 回归 | `tests/test_minio_s3_paths.py` 7 条 |

### P3 · `freemarker_ssti` 把「要鉴权」当「不存在」

| 项 | 内容 |
|---|---|
| 发现方式 | 建 C4-4 之前，先在 R10（真实 JeecgBoot 3.6.3）上复现 |
| 现象 | 真实站判 **SAFE**；实际是接口要 Token |
| 根因 | 真实响应是 `HTTP 200 + {"code":500,"message":"Token校验失败，无权限访问！"}`，三个特征叠在一起让通用兜底 `_DENY_RE` 全部抓不到：<br>状态码期望 401/403 实际 **200**；body code 期望 401 实际 **500**；文案期望"认证失败"实际"无权限访问" |
| 影响面 | 所有 JeecgBoot 站点（jmreport 接口默认都要 Token） |
| 修复 | `29f460b` 插件自做鉴权墙判定 → UNKNOWN；判定顺序放在 SSTI 求值判定**之前** |
| 回归 | `tests/test_freemarker_ssti_authwall.py` 9 条 |

### P4 · `ruoyi_gen_rce` 只探可达性，有洞也报不出来

| 项 | 内容 |
|---|---|
| 发现方式 | 建 C4-5（真实 Freemarker 渲染 `tableName`）后扫描 |
| 现象 | 真实存在 SSTI 的站点判 **UNKNOWN** |
| 根因 | 只 GET `/tool/gen/edit` 探可达性；有 SSTI 和没 SSTI 的真站都返回 200 HTML，无法区分 → 一律 UNKNOWN。另有一条 `X-Ruoyi-Vuln: gen-ssti` 签名头后门，真实站点永远不会返回 |
| 影响面 | 所有启用代码生成模块的若依站点 |
| 修复 | `8ad0512` 改为对 `/tool/gen/preview` 做差分（基线无 49 / 注入有 49 / 无载荷回显，三条缺一不可） |
| 回归 | `tests/test_gen_rce_differential.py` 8 条 |

## 这四条的共性 —— 报告里该写的方法建议

| 共性 | 说明 |
|---|---|
| **路径靠想象** | P1/P2/P4 都是「探的路径不是真实产品路径」。真实产品不按扫描器的想象布置路由 |
| **SAFE 兜底掩盖问题** | P1/P2 判 SAFE、P4 判 UNKNOWN，看起来都「很正常」—— 盲测跑一遍根本看不出异常 |
| **只有真实形态靶场能碰出来** | 签名靶场（返回约定 marker）永远暴露不了这四个 |

### 对盲测方法论的启示

**P1–P4 说明：光靠「跑一遍扫、看结果」的盲测，测不出「路径猜错」这类缺陷。**

因为猜错的路径返回 404/SAFE，报告里显示为「不存在该漏洞」—— 一个完全合理的结论。
没有 ground truth 对照，无法区分「真的不存在」和「根本没探到」。

这正是阶段 2 必须做**三方对照**（扫描器 / 手工探测 / nuclei）而不是只看扫描器输出的原因。
