## 为什么 GT 会测不到

分离版站点的管理端点（Druid / Swagger）**匿名可达**，但 GT 的通用探测用的是
`/druid/index.html`、`/swagger-ui/index.html` **根路径**，而真实路径在 `/prod-api/` 下。

GT 想探 `/prod-api/` 时又遇到 401/302（部分端点被登录墙挡），于是判「不可判定」。

**这是 GT 的探测盲区，不是扫描器的问题。**

## 唯一的真 FN：R1 的 `/docs/ry_20210415.sql`（不修，属设计边界）

### 事实

```
GET /docs/ry_20210415.sql  →  200 / 12595 字节   ← 真实存在
扫描器：UNKNOWN
```

### 我试过修，但方向错了

`backup_scan` 只探根路径的 5 个固定文件名 × 若干后缀，不覆盖子目录。
我加了一段「常见遗留目录 × 常见扩展名」的探测，实测**仍然检不出**。原因：

```
GET /docs/          →  404（目录不可列）
GET /docs/docs.sql  →  404（真实文件名是 ry_20210415.sql，猜不到）
```

**目录不可列 + 文件名未知 → 字典法本质上无解。** 这不是"字典少了几条"，
是这一类文件的**文件名不可预测**（建库脚本通常带日期：`ry_20210415.sql`）。

### 决定：不改，写进报告的已知边界

硬凑字典（枚举日期、加更多前缀）只会：
1. 把扫描时间拖长几倍
2. 命中率仍然极低
3. 引入新的误报面

**诚实的做法是承认这个边界**，而不是用「看起来覆盖更广」的无效探测充数。

### 给使用者的建议

需要覆盖这类泄露时，应在**拿到线索后定向验证**：
- 从 HTML/JS 里提取的文件名
- 从 `.git`/`.svn` 泄露出的文件列表
- 已知业务命名规律（如 `ry_YYYYMMDD.sql`）

或者用 `--crawl` / `--js-extract` 先收集路径再探测。

### 附：`source_leak` 的情况

它也只认固定路径（`.svn/entries`、`.idea/workspace.xml` 等），
但那些是**有确定文件名**的 —— 这类能覆盖，且 R7 上实测有效
（`.svn/entries` + `.idea/workspace.xml` 都 CONFIRMED）。
两类文件的区别在于「文件名是否可预测」，不是插件质量差异。
