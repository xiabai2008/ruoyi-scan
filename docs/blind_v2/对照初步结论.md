## 一、最重要的发现：nuclei 的覆盖面极小

**27 个目标，nuclei 只在 1 个站（C1-1）有命中，共 9 条。**

```
非 P 类小计：扫描器 49 条 CONFIRMED，nuclei 9 条命中
```

这不是 nuclei 的问题 —— 它的 13000+ 模板针对的是**有公开 CVE/POC 的已知漏洞**，
而本靶场复刻的是**配置类与业务逻辑类**问题（默认口令、未授权、SSTI、路径猜错），
这些不在 nuclei 的模板体系里。

**方法论结论**：nuclei 作为第三方基准，对这类靶场的交叉验证价值有限。
它能证实「有明确 CVE 的东西」，但无法证实/证伪「配置与逻辑判断」。
真正的裁判只能是**独立的 ground truth 探测**。

## 二、nuclei 自己也会误报

C1-1 上 nuclei 报了一条 `jolokia-logback-jndi-rce`（high），而扫描器没报这条。

**核实结果：nuclei 这条是误报。**

它只看到 `/actuator/jolokia/list` 的响应体里含 `logback` 字样就判 high，
**没有验证 JNDI 可利用性**：

```
匹配的 URL：http://127.0.0.1:19301/actuator/jolokia/list
响应体前 300 字节：{"request":{"type":"list"},"value":{"JMImplementation":...
body 含 logback: True
body 含 JNDI:   False     ← 关键：根本没有 JNDI 利用的迹象
```

Jolokia 是 JMX over HTTP 的通用桥，只要 JVM 里有 logback（几乎所有 Spring Boot 应用都有），
它的 MBean 列表里就会出现 logback —— 这只证明「logback 在跑」，不证明「能用 JNDI 打」。

**方法论结论**：第三方基准也会用「关键词命中」冒充漏洞验证。
不能因为「nuclei 报了而扫描器没报」就认定扫描器漏报 —— 必须回到 ground truth。

## 六、C4-4 / C4-5 判 0 的根因（已核实）

**恢复环境后单独复测，确认是真漏报，不是靶场问题。**

### 现象

```
C4-4（jmreport SSTI）：
  靶场验证：POST connUrl=${7*7} → 响应 "query=49"   ✅ 模板真的求值
  扫描器：  0 CONFIRMED，插件数 26
  指纹：    cms=spring（命中 root_json:timestamp,status,error,path）

C4-5（代码生成 SSTI）：
  扫描器：  0 CONFIRMED，插件数 26
  指纹：    cms=spring
```

### 根因：CMS 识别错 → 插件包不加载

靶场首页是 Spring Boot 默认错误 JSON（`{"timestamp","status","error","path"}`），
指纹据此判成 `spring`。于是：

- `plugins.jeecgboot` **整包不加载** → `freemarker_ssti` 没跑
- `plugins.ruoyi` **整包不加载** → `ruoyi_gen_rce` 没跑

两个插件的判定逻辑本身没问题（我在建靶场时手工验证过能 CONFIRMED），
**它们根本没被调用**。

### 这是架构层面的真缺陷

一个错误的指纹判定，会导致**整个插件包**的漏洞面全部漏报。
比"某个插件判定不准"严重得多。

触发条件很常见：任何返回 Spring Boot 默认错误 JSON 的首页，
都可能被误判成 `spring`，从而屏蔽掉 ruoyi/jeecgboot 的全部专项插件。

### 修复方向（待做）

1. **指纹不确定时不该排他**：`cms=spring` 置信度只有 0.5（弱特征），
   此时应同时加载 spring + ruoyi + jeecgboot 三个包（像 F7-1 已经对
   `cms=""` 做的回退那样），而不是只加载 spring。
2. 或者：把"命中 root_json"这种弱特征的阈值调高，不单独构成 cms 判定。

### 报告里怎么归类

这不是 P 类（P 类是我建靶时预先发现的），而是**盲测发现的真缺陷**，
要计入盲测检出。而且它影响面大（两类插件包），应排在修复优先级前列。

## 七、GT 判据自身的问题（已修正）

做对照时发现 **GT 最初有 20 条假 FN**，根因是我的 `really_exists()` 漏识别了两类框架 catch-all：

| 靶场 | catch-all 形态 | 例 |
|---|---|---|
| C1-4 Spring Cloud Config | `/{name}/{profile}` 对任意两段路径返 200 JSON，**回显请求名** | `GET /.git/HEAD` → `{"name":".git","profiles":["HEAD"]}` |
| C2-3 Cloud Function | 任意路径返极短字符串，**内容是路径本身** | `GET /.git/HEAD` → `"HEAD"` |
| C4-6 Thymeleaf 靶场 | `/**` 路由把路径当页面标题回显 | `GET /.git/HEAD` → `<h2>页面: .git/HEAD</h2>` |

补了 `is_path_echo()` 识别这三类后，FN 从 23 降到 1，FP 归零（后又因 C4-6 复现为 6，见下）。

**教训**：ground truth 自己也会错，必须先自检。这也是三方对照的价值 ——
如果只有 GT 一家，这 20 条假 FN 会被当成扫描器的锅。

## 八、盲测发现的真误报：catch-all 路径回显被当成漏洞（C4-6）

C4-6 扫描器报了 3 条 CONFIRMED，全部是误报：

| 插件 | URL | 实际响应 |
|---|---|---|
| RocketMQ Dashboard 未授权 | `/rocketmq/` | `<html><body><h2>页面: rocketmq/</h2></body></html>` |
| RuoYi Swagger 未授权访问 | `/swagger-ui.html` | `<html><body><h2>页面: swagger-ui.html</h2></body></html>` |
| 未授权访问（批量） | `/` | 同上（因 swagger-ui 出现在正文） |

**根因**：C4-6 靶场有 `/**` catch-all 路由，把请求路径当页面标题回显。
扫描器看到「响应体里出现 rocketmq / swagger-ui 字样」就判命中，
**没有识别「这只是把请求路径回显出来」**。

这与 C1-4（Config Server 回显）是**同一类缺陷**：
路径类插件用「关键词出现」做判定，而 catch-all 路由会让任意关键词都出现。

**影响面**：所有带 catch-all 路由的站点（任何 SPA、任何 `/**` 路由的后端）。
盲测 v1 报告里记过类似的（4.8 错误页回显路径），但显然没修彻底。

**这是本次盲测最有价值的发现之一** —— 它证明「按真实形态建靶场」能持续挖出这类问题。
