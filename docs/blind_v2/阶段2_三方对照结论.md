## 二、三条核心结论

### 结论 1：nuclei 对这类靶场的交叉验证价值极低

27 个目标，只有 C1-1 有命中（9 条，其中 8 条是同一个 jolokia-info-disclosure 模板）。

原因不是 nuclei 弱，而是**覆盖面不重叠**：它的 13000+ 模板针对有公开 CVE/POC 的漏洞，
本靶场复刻的是**配置类与逻辑类**问题（默认口令、未授权、SSTI、路径猜错），
这些不在它的模板体系里。

**nuclei 还出现了误报**：`jolokia-logback-jndi-rce` 只看到响应体含 `logback` 就判 high
（body 里 `JNDI` 出现次数为 0），而扫描器没报这条 —— 这次是**扫描器对、nuclei 错**。

> **方法论**：第三方基准也会用「关键词命中」冒充验证。不能因为「nuclei 报了扫描器没报」
> 就认定扫描器漏报，必须回到 GT。

### 结论 2：盲测发现一个高影响面误报（catch-all 路径回显）

**C4-6 上 3 条 CONFIRMED 全是误报**：

```
GET /rocketmq/       → <html><body><h2>页面: rocketmq/</h2></body></html>
GET /swagger-ui.html → <html><body><h2>页面: swagger-ui.html</h2></body></html>
```

靶场有 `/**` catch-all 把路径当页面标题回显，扫描器看到正文含 `rocketmq`/`swagger-ui`
就判命中，**没识别出「这只是把请求路径回显出来」**。

**影响面**：所有带 catch-all 路由的站点（任何 SPA、任何 `/**` 路由后端）。
与 C1-4（Spring Cloud Config 回显）同源 —— 盲测 v1 报告记过类似问题但没修彻底。

**这是本次盲测最有价值的发现**：证明「按真实形态建靶场」能持续挖出这类问题。

### 结论 3：指纹误判会导致整包插件不加载（架构级漏报）

**C4-4 / C4-5 判 0 的根因**（已复测确认，非靶场问题）：

```
C4-4 靶场：POST connUrl=${7*7} → 响应 "query=49"   ✅ 模板真的求值
C4-4 扫描：0 CONFIRMED，指纹 cms=spring，插件数 26（无任何 jeecg 插件）

C4-5 扫描：0 CONFIRMED，指纹 cms=spring，无任何 ruoyi 插件
```

靶场首页是 Spring Boot 默认错误 JSON（`{"timestamp","status","error","path"}`），
指纹据此判成 `spring` → `plugins.jeecgboot` / `plugins.ruoyi` **整包不加载**
→ `freemarker_ssti` / `ruoyi_gen_rce` 根本没被调用。

**这比「某个插件判定不准」严重得多**：一个错误指纹判定，屏蔽掉整个插件包的漏洞面。
触发条件很常见 —— 任何返回 Spring Boot 默认错误 JSON 的首页都可能中招。

## 三、GT 自身的问题（重要教训）

做对照时发现 **GT 最初有 20 条假 FN + 6 条假 FP**，根因是我的 `really_exists()` 漏识别三类 catch-all：

| 靶场 | catch-all 形态 |
|---|---|
| C1-4 Spring Cloud Config | `/{name}/{profile}` 任意两段路径返 200 JSON，回显请求名 |
| C2-3 Cloud Function | 任意路径返极短串，内容就是路径本身 |
| C4-6 Thymeleaf 靶场 | `/**` 路由把路径当页面标题回显 |

补 `is_path_echo()` 后修正。**还踩了一个反向坑**：判据从「seg 出现在 text 里」
收得太宽时，`.git/HEAD` 的内容 `ref: refs/heads/master` 含 `head`，
被误判成回显 → 真漏洞漏报。最终要求「去掉路径段后几乎不剩东西」。

> **教训：GT 自己也会错，必须先自检。** 三方对照的价值正在于此 ——
> 如果只有 GT 一家，那 20 条假 FN 会被当成扫描器的锅。
