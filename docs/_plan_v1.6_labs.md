## 一、现状：30 座靶场，31 个插件只有单一验证来源

盲测 v4 共 48 个插件有 CONFIRMED 产出。但按「该插件在几个站点产出过」统计：

**其中 31 个（65%）只在 1 个站点验证过。**

单点验证的含义不是「验证不足」，而是**「换一个站点形态就可能失效」**——
插件在 A 站能报出来，不代表在 B 站也能，因为判定依赖的是响应形态。

## 三、已核实的两个「单点」成因（不是靶场缺口）

### 3.1 Thymeleaf/SpEL 只在 C4 —— 正常，靶场确实有该服务

初稿标了「归因可疑」，已人工核对推翻。C4-6 的响应（真实请求复现）：

```
GET /__$%7B7*7%7D__::.x   → 500
org.thymeleaf.exceptions.TemplateInputException:
  Error resolving template [49::.x]        ← 路径里的 ${7*7} 被求值成 49
SpEL 求值: ${7*7} = 49
```

**是真命中**：模板名里的 `${7*7}` 确实被求值了。C4-6 就是一个可求值的 thymeleaf 服务，
单点是「只有这一座靶场有 thymeleaf 形态」，不是误报。

### 3.2 POST型报错注入（role/dept）只在 R1 —— 需要**高权会话**，与低权账号无关

初稿写「靠 `--surface-account` 低权账号」，**错了**。逐轮核对：

```
R1-anon    → UNKNOWN（未取得高权会话）
R1-auth    → CONFIRMED  ← 真正的来源
R1-surface → CONFIRMED
```

这两个插件声明了 `requires_auth = True`，靠 `--auth-login` 的高权会话做差分，
不需要低权账号。

**顺带核实了 `scanner_low` 的真实分布**（逐个 grep `seed/r*_business.py`）：

| 站点 | `scanner_low` |
|---|---|
| R2 / R3 / R4 / R5 / R6 / R7 | ✅ 有 |
| R1 / R8 / R9 / R10 | ❌ 无 |

> 两次修正记录：初稿（凭记忆）写「只有 R1-R5 有」——**R1 恰恰没有，R2-R7 才有**。
> 又写「这两个插件靠低权账号」——**它们靠高权会话**。
> 两条都是没核实就下结论，逐条 grep + 逐轮核报告后才纠正。

→ **不是靶场缺口，也不是账号问题，是「只有 R1 跑了 --auth-login 的有效扫描」**。
其它站点若也跑带 `--auth-login` 的扫描，同样能验证（盲测 v4 里 R3/R4/R5 的 auth 轮没覆盖到这两个插件的原因待查）。

## 四、v1.6 该造哪几座（按 ROI 排序）

### P0 · C5「暴露但需认证」（**最高优先级**，且不依赖任何新版本）

**为什么必须造**：v1.6 已实现的 A2（未授权类会话隔离）**当前无法端到端验证**——
现有靶场没有「接口存在但需认证」的形态。R1/R7 的相关端点根本不存在（登录后仍 302）。

| 项 | 设计 |
|---|---|
| 形态 | Swagger / Druid / Actuator **存在且可访问，但需登录** |
| 未认证扫描 | 全部 SAFE（302 到登录页） |
| **已认证扫描** | **不得 CONFIRMED**，应为 UNKNOWN（`looks_authenticated` 命中）或 SAFE |
| 实现 | nginx `auth_request` 或 Spring Security 加一条规则，**不改 Java 源码** |
| 成本 | 低（复用 R7 的 dist + 后端，加一层认证） |
| 解锁 | 验证 A2 的核心断言；同时可作为「未授权类插件在认证站点上不误报」的回归靶场 |

**没有它，A2 的 `looks_authenticated` 就是一行没被验证过的代码。**

### P1 · Y1「芋道 yudao 真实站」（**扩框架的前置**）

| 项 | 设计 |
|---|---|
| 形态 | 芋道真实站（Spring Boot 3.x 分支），含 `/admin-api` 前缀 |
| 版本 | 优先能复现公开 CVE 的版本 |
| 验证点 | `/system/tenant/simple-list` 免鉴权探针是否可用；`/jmreport/**` 的 `permitAll` 在真实部署里是否仍生效 |
| 成本 | 中（需拉源码 + Maven 构建 + MySQL） |
| 解锁 | `plugins/yudao/` 的 6–8 个插件；WP-U1（JSON 信封鉴权墙）的真实验证 |

**风险**：若 `/jmreport/**` 在二开里被收紧，4 个复用插件要从「直接复用」降级为「路径复用、判据重写」。
**必须先建站验证，再定插件方案**——这与 v1.5.6 WP3（Plus 定时任务）的教训一致。

### P2 · R14「未授权文件读取点」—— **调研后放弃，该漏洞在现有版本上不存在**

**原计划**：R1 的 `/common/download/resource` 需登录，做一个匿名可达的副本解锁 2 个零产出插件。

**实际做了什么**（2026-11-02）：
1. 复制 `src/R1` → `src/R14`（101MB），在 Shiro 匿名清单加 `/common/download/resource`
2. Maven 重建成功（JDK17，69MB jar），R14 启动成功（19114 → 19241）
3. 验证匿名放行生效：**R14 返回 200，R1 返回 302** ✅

**但漏洞不存在**：所有穿越 payload 都返回 `200 + 0 字节`。读源码确认：

```java
// FileUtils.checkAllowDownload()  —— R1(4.5.1)/R2(4.6.2)/R3(4.7.8)/R4(4.8.0)/R5(4.8.3) 全部含
if (StringUtils.contains(resource, "..")) { return false; }   // 禁止目录上跳
```

且 `resourceDownload()` 的 `catch (Exception e) { log.error(...) }` 会吞掉异常 →
匿名可达也只是返回空内容。

**顺带修正了一个插件声明错误**：`file_read` / `file_read_path` 原本声明
`affected_versions = ">=3.0,<4.7"`（表示 4.7 之前都受影响），但 4.5.1/4.6.2 实测
均有 `..` 拦截。错误的版本区间比不设区间更糟——它会让插件在**真实受影响的目标上
反被跳过**（这正是 `file_upload`/`job_rce` 注释里记录过的教训）。
现改为不设版本门，完全交给响应证据判定。

**R14 已清理**（源码/构建产物/运行目录/nginx 配置全部移除，lab 仓库回到干净状态）。

**结论**：这 2 个「零产出」插件维持零产出是**正确行为**——目标上确实没有该漏洞。
若将来要验证检出能力，需要一个真正含未校验 `..` 的旧版本（4.4 及更早），
但那样靶场就与「真实客户现场」脱节了，ROI 不高。

### P3 · Plus 5.5 误配站（解锁 `plus_job_unauth`）

| 项 | 设计 |
|---|---|
| 形态 | RuoYi-Vue-Plus **5.5.x**（SnailJob 迁移之前）+ `security.excludes` 放开 `/monitor/**` |
| 成本 | 中（需拉 5.5 源码 + 构建） |
| 优先级理由 | 只解锁 1 个插件；且该插件已在 5.6.2 上验证了「端点不存在判 UNKNOWN」的正确行为，**不修也不算漏报** |

### 不做

- **不为 spring 域再造靶场**：C1/C2 已覆盖 10 个 spring 插件，单点问题主要来自「ruoyi 站点不加载 spring 包」（P1-3，属代码问题不是靶场问题）
- **不为 jeecg 再造靶场**：R10 已 8/8，除非要做 jeecg 的「需认证版」来验证 P1-4
- **不造通用靶场**：ROADMAP 自己写了「不做大而全」
