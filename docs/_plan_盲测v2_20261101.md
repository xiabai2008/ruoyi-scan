#### 三个 SSTI 靶场（C4-4/5/6）—— 全部用真实模板引擎

**这是本轮最重要的变化：从「marker 桩靶场」转向「真实引擎靶场」。**

签名靶场返回约定 marker、插件匹配 marker —— 那种靶场永远证明不了真实检出能力。
这三个靶场都用真实模板引擎求值，扫描器必须真的构造出会被求值的表达式才可能命中。

| 靶场 | 端口 | 求值机制 | 实测 |
|---|---|---|---|
| C4-4 jmreport | 19081 | 真实 Freemarker 渲染 `connUrl` | `${7*7}`→`49`，插件 CONFIRMED |
| C4-5 代码生成 | 19082 | 真实 Freemarker 渲染 `tableName` | `sys_user_${7*7}`→`sys_user_49`，CONFIRMED |
| C4-6 Thymeleaf | 19083 | 真实 SpEL 求值 `__${}__` | 视图名→`49::.x` + `org.thymeleaf` 异常，CONFIRMED |

三个插件**全部首次被证明能检出**。

**同时挖出三个确定性缺陷**（都已修）：

| # | 插件事 | 缺陷 | 修法 |
|---|---|---|---|
| 1 | `freemarker_ssti` | 真实 Jeecg 要 Token，返回 `HTTP 200 + {"code":500,"message":"Token校验失败"}`。三个特征叠加（状态码 200 / body code 500 / 文案"无权限"）让通用兜底 `_DENY_RE` 全抓不到 → 判 **SAFE**（把"没资格测"写成"确认不存在"） | 插件自做鉴权墙判定 → UNKNOWN |
| 2 | `ruoyi_gen_rce` | 只 GET `/tool/gen/edit` 探可达性。有洞没洞都拿到同样的 200 HTML → 一律 UNKNOWN，**有洞也报不出来**。另有一条 `X-Ruoyi-Vuln: gen-ssti` 签名头后门 | 改为对 `/tool/gen/preview` 做差分（基线无 49 vs 注入有 49 vs 无载荷回显） |
| 3 | `thymeleaf_ssti` | 判定逻辑本身正确（49 + 引擎特征），但从未有真实靶场验证 | 建 C4-6，验证判定成立 |

**C4-5 靶场侧的两个实测坑**（写下来避免重复踩）：
1. `tableName=sys_user_${7*7}` 直接在 URL 里发，Spring 会把 `{}` 当路径变量边界吃掉，
   服务端收到 `sys_user_$7*7`，失去求值能力 —— **必须 URL 编码成 `%24%7B7*7%7D`**
2. C4-6 用 `request.getRequestURI()` 拿到的是**未解码**串（`%24` 仍是 `%24`），
   必须显式 `URLDecoder.decode` —— 真实 Spring MVC 路由匹配用的是解码后的值

**探针设计原则**：三个 SSTI 靶场的探针都不是"检查端口 200"，而是
**真的发一次 `${7*7}` 并断言响应出现求值结果**。只检查端口会把「服务起了但模板引擎
没接对」当成健康 —— 那时靶场其实是坏的，后续所有盲测结论都不可信。

### 0.7 靶场契约对齐（来自 04 行为契约的核验结论）

设计文档 `04_行为契约.md` + `08_真实性核验表.md` 直读官方 tag 源码核验出的 **10 条全局禁止项**，
其中几条直接推翻「修靶场」的直觉做法。**这些不是造错，是官方真实行为，一律不许"修"**：

| 现象 | 真实原因 | 禁止的做法 |
|---|---|---|
| `/captcha/captchaImage` 不带 `?type=` 返回 200 但 **0 字节 body** | `ImageIO.write(null,...)` 抛 `IllegalArgumentException` 被 catch 吞掉（源码原样） | 不许"修"成默认 math |
| 表单字段是 `rememberme`（全小写），Controller 形参写 `rememberMe` | Spring 绑定失配，若依既有小瑕疵 | 不许"修正"成 camelCase |
| 越权页渲染 `RuoYi-403` 但 **HTTP 状态码 200** | 官方行为 | 不许改成真 403 |
| 分离版鉴权失败 **HTTP 恒 200**，语义在 body `code:401` | 官方行为 | 不许改成 HTTP 401 |
| 单机版 4.x **全部版本 pom 都没有 actuator 依赖** | 事实 | 不许给 R1–R5 加 `/actuator/*` |
| 单机版没有 `/prod-api/`、`/getInfo`、`/captchaImage`（无前缀） | 事实（这三个是 Vue 版接口） | 不许加 |
| Druid `ruoyi/123456` + `enabled:true` + `allow:` 空 | **官方默认值**，不是运维忘关 | 不许当成"配置失误"改掉 |
| favicon 5 个版本同一 md5 `e49fd30e...`、均 16958 字节 | 官方多年没换 logo | **绝对不许换**（见下） |
| 静态资源 `?v=4.x.y`、页脚年份随版本变 | 官方 | 不许统一 |

**favicon 是若依识别的独木桥**（08 核验表第 3 节）：扫描器 ruoyi 的 3 个 strong_paths
（`/prod-api/`、`/captcha/image`、`/getInfo`）**全落空**、3 个 login_keywords 也全落空，
最终只靠 favicon(+0.5) + 弱词"若依"(+0.2) = 0.7 才判 ruoyi。**favicon 一换 → 置信度跌到 0.2 < 0.4
阈值 → `cms=""` → 整站扫不出任何东西。** 这解释了现网大量若依站点为什么扫不出来。

> 注意：这意味着靶场里 favicon 一旦被"品牌化"（换成虚构单位的 logo），扫描器就瞎了。
> **装饰性品牌化只能改 `<title>` 文案与业务 UI，不能动 favicon** —— 至少保留一座站用原版 favicon
> 作为基线。

**已定（2026-11-01）**：**R1 保留若依原版 favicon**（`e49fd30e...` / 16958 字节）作为基线对照组，
R2–R11 按虚构单位品牌化。这样一次盲测同时覆盖两种真实场景：

| 站 | favicon | 预期 `cms` | 测什么 |
|---|---|---|---|
| R1 | 原版逐依 | `ruoyi` 0.7 | 基线：能扫出来时结论对不对 |
| R2–R11 | 虚构单位 logo | 可能 `cms=""` | 真实短板：品牌化后是否整站盲 |

**这不是"给扫描器留活路"，而是把 favicon 当成一个受控变量** —— 同一个工具，两种结果，
正好量化"识别链路对单一特征的依赖有多脆"。

**已核实（2026-11-01 实测）**：R1 当前 favicon 就是原版，无需改动。

## 阶段 0 附带：今天新发现的扫描器缺陷（F9）

盲测 v1 没测出来，因为当时靶场没有真的 `.git`/`.env`。**这条建议在阶段 0 之后立刻修**。

**现象**：p1 分支 `core/orchestrator.py:719-733` 用 base_path **全局重写** plugin_target：

```python
plugin_target = target
api_base = detect_api_base(target, session)
if api_base:
    plugin_target = target.rstrip("/") + api_base + "/"
engine.run(classes, plugin_target, ...)   # 所有插件都拿到带前缀的 target
```

**后果实测**（mock 站：根路径真放 `.git/HEAD` 与 `.env`，API 在 `/prod-api`）：

```
/.git/HEAD  → 200 "ref: refs/heads/main"
扫描器探    → /prod-api/.git/HEAD → 502
判定        → SAFE「状态码=200, 未检测到 .git 泄露」   ← 错误 SAFE
.env        → 同样 SAFE
```

**根因**：`.git`/`.env`/备份/IDE 残留/sourcemap/`/logs/` 是**部署在 web 根上的静态资源**，
不会出现在 `/prod-api` 下面；API 类端点才在 base_path 下。现在一刀切全推走了。

**影响面**：至少 9 个插件（`git_leak`/`env_leak`/`backup_scan`/`source_leak`/`swagger_leak`/
`dir_listing`/`actuator_unauth`/`jolokia_rce` + R7 的 sourcemap 无插件）。

**修法**：给插件声明「路径作用域」（root / api / both），或两条都探命中任一即算。
须跑 `pytest tests/test_fp_baseline.py`，新增误报登记 `KNOWN_FALSE_POSITIVES`。

### 07 要求的 13 条陷阱对照表（Phase 2 统计时必须逐条过）

设计文档 07 §4 的 13 条（4.0 开场 + 4.1–4.12），每条都是"曾经真实踩过"的具体现象。

| 4.4 | **WAF 403 被判 SAFE** | R12 上是否出现"真实存在的洞判 SAFE"（应为 UNKNOWN） |
| 4.5 | 登录墙让"存在/不存在"趋同 | 随机路径 vs 真实路径的 md5 是否逐字节相同 |
| 4.6 | 时间线不一致露馅 | 文件 mtime / SQL create_time 是否全刷成今天 |
| 4.7 | Spring Boot 4 把"资源不存在"包成 200+JSON | soft404 在 `No static resource` 上是否失效 |
| 4.8 | **错误页回显路径 → 组件探测误判** | `/rocketmq/`、`/minio/` 这类路径名是否被当证据 |
| 4.9 | 未授权可达性必须在**匿名**会话判定 | `--auth` 注入后是否误判 `job_rce` 等 |
| 4.10 | 分离版不探 base-path 等于没扫 | 检出率是否为 0 |
| 4.11 | 分离版登录墙 200+JSON 回显路径 | 假备份/假组件是否被当存在 |

## 阶段 2 · 三方对照

| 站点 | 插件数 | TP | FP | FN | 精确率 | 召回率 |
|---|---|---|---|---|---|---|

### 「结果太差怎么办」四步排查（07 第七节，不许跳过）

看到结果差，**先排查环境，再怀疑扫描器**：

1. 站点是否真起来 → `lab.py verify <组>` 全 UP？登录页版权年份对不对？
2. 是否被版本过滤杀了 → `--cms ruoyi` 或关掉版本过滤再跑
3. 鉴权是否断了 → `admin/admin123` 能进？登录失败会让一批插件全变 UNKNOWN
4. payload 是否打偏 → 单插件跑，看请求日志

> **最忌讳**：看到结果不好直接改靶场迎合扫描器 —— 那这套环境就废了，
> 它的全部价值就是"它不知道扫描器存在"。

## 抗拟合机制（贯穿全程）

你担心的"靶场对照扫描器源码开发 → 效果理想化"，根因是**靶场按插件清单反推该测什么**。三条破解：

1. **从上游反推**：用若依/Jeecg 官方 changelog、CVE、issue 决定该有哪些漏洞，而不是从 `plugins/` 目录反推。
2. **从第三方反推**：nuclei 模板库里有现成的 RuoYi/Spring 检测，作为第二意见。
3. **每轮留 hold-out**：R12 全程不参与修复循环；必要时新建一座站也只用于最终验证。
