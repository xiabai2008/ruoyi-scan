 Ruoyi-Scan 使用指导（场景 · 方法 · 技巧）
 版本：v1.5.2
 配套：ruoyi-scan-command-manual.txt（全部命令）、ruoyi-scan-plugins.txt（POC 清单）
 适用：已获得书面授权的渗透测试 / 安全自查 / 等保测评 / DevSecOps
===============================================================================

【先读这一段】
    这个工具只做一件事：在你被授权的前提下，把「这台若依到底有没有某个漏洞」
    验证清楚，并给出可交付的证据与报告。它不负责找资产、不负责拿 shell、
    不负责绕过你的授权边界。
    没有书面授权就不要扫。扫描行为本身就是入侵特征，会进对方日志。


===============================================================================
 0. 30 秒判断：这次该不该用 Ruoyi-Scan
===============================================================================

    满足下面全部条件，才继续：
    [1] 目标在授权范围内（域名 / IP / 端口 / 路径都写清楚）
    [2] 时间窗允许主动扫描（避开业务高峰与封网期）
    [3] 目标是若依（RuoYi）或其衍生框架，或你不确定、想确认是不是
    [4] 你接受「扫描会产生请求日志、可能触发 WAF 与告警」这一事实

    任意一条不满足：
    - 只想看资产指纹、不想产生攻击流量 → 用浏览器 / 被动代理，别用主动扫描
    - 目标是纯静态站或非 Java 系统 → 用通用扫描器，Ruoyi-Scan 会大量 UNKNOWN
    - 没有授权 → 停，什么都别做


===============================================================================
 1. 它擅长什么、不擅长什么
===============================================================================

1.1 擅长
-------------------------------------------------------------------------------
    - 判断目标是不是若依，以及是哪个变体（Vue3 / App / Plus / Cloud-Plus / Magic）
    - 若依 + Spring 生态的已知漏洞验证（54 个 POC，其中若依专项 20 个）
    - 登录后的越权与资产盘点（--auth-surface）
    - 把「测过但不存在」写成 SAFE，把「测不了」写成 UNKNOWN，报告可交付
    - 整改复测：同一目标两次扫描做差异，证明洞真的修了

1.2 不擅长（别指望它）
-------------------------------------------------------------------------------
    - 0day / 逻辑漏洞挖掘：它只验证已知模式，业务逻辑要靠人
    - 无差别的目录爆破：字典是若依相关路径，不是通用大字典
    - 绕过强对抗 WAF：--adversarial-transport 只覆盖 Cloudflare / JS 挑战这一类
    - 内网横向、提权、持久化：工具明确不做，也不该做
    - 非 Java 系统：PHP / .NET / Node 站点跑出来基本全是 UNKNOWN

1.3 和通用扫描器的分工
-------------------------------------------------------------------------------
    通用扫描器（nuclei / xray）：广度优先，告诉你「这里可能有问题」
    Ruoyi-Scan：深度 + 判定纪律，告诉你「这个版本的这个洞，到底有没有」
    实战顺序：先用通用扫描器铺面，命中若依特征后再用本工具收敛结论。


===============================================================================
 2. 三分钟决策：先跑哪个模式
===============================================================================

2.1 决策树（照着走）
-------------------------------------------------------------------------------
    目标是不是若依？
      ├─ 不知道
      │    └─ ruoyi-scan -p <url> --time-budget 60
      │         （-p 会先做指纹；不是若依就不会浪费大量 POC 请求）
      ├─ 确定是，且只要能出结论
      │    └─ ruoyi-scan -p <url> --report .\reports\demo
      ├─ 确定是，要完整评估（含目录、弱口令）
      │    └─ ruoyi-scan -u <url> --report .\reports\full
      ├─ 只想看有哪些后台 / 敏感文件
      │    └─ ruoyi-scan -m <url>
      ├─ 只想验证弱口令
      │    └─ ruoyi-scan -l <url> --pass-level top100
      └─ 已经登录，要测越权
           └─ ruoyi-scan -u <url> --auth-login 账号:密码 --auth-surface

2.2 四模式对照
-------------------------------------------------------------------------------
    模式        命令        请求量    典型耗时（单目标）   适合
    漏洞检测    -p          小        10 秒 - 1 分钟       复测、批量铺面、CI
    目录扫描    -m          中        1 - 3 分钟           摸攻击面、找后台
    综合扫描    -u          大        3 - 10 分钟          首次完整评估
    登录爆破    -l          很大      1 - 10 分钟          弱口令专项

    耗时随目标响应速度、WAF、字典级别变化，上表是内网靶场量级。

2.3 规模与节奏（重要）
-------------------------------------------------------------------------------
    单个生产目标：    --threads 5  --rate 10  --timeout 15
    内网批量（<50）：  --threads 8  --rate 20
    大规模铺面：      -f targets.txt -p --time-budget 60 --threads 10 --rate 30
    护网 / 值守期间：  --rate 5，先跟对方确认告警阈值

    任何时候都不要用 --threads 50 打生产库，打挂了不是漏洞，是事故。


===============================================================================
 3. 六个真实场景（照着套）
===============================================================================

3.1 场景 A：接手一批资产，不知道哪些是若依
-------------------------------------------------------------------------------
    背景：甲方给了 200 个 URL，要求「先看看有多少个若依」。
    目标：只做指纹与快速验证，不深挖，控制总时长。

    第一步，批量铺面：
    ruoyi-scan -f targets.txt -p --time-budget 60 --threads 10 --rate 30 --report .\reports\recon

    第二步，看每个目标开头的指纹行：
    [*]指纹识别：cms=ruoyi 置信度=0.70 命中=['login:RuoYi', 'keyword:若依']
    命中 ruoyi 的挑出来，进场景 B；命中 spring 的可用 --cms spring 再跑一轮。

    注意：
    - 这一步用 -p 不用 -u：-u 会对每个目标做目录扫描和爆破，200 个目标会跑很久。
    - --time-budget 60 表示单目标最多 60 秒，超时插件记 UNKNOWN，不会卡死整批。

3.2 场景 B：确认是若依，有授权，要挖深
-------------------------------------------------------------------------------
    这是最主要的场景。推荐顺序（不要跳步）：

    第一步，摸攻击面（不产生攻击 payload）：
    ruoyi-scan -m http://target:8080/ --report .\reports\dir

    第二步，跑 POC 拿结论：
    ruoyi-scan -p http://target:8080/ --components --report .\reports\poc

    第三步，有账号的话，登录后重跑（很多洞只在登录态下可见）：
    ruoyi-scan -u http://target:8080/ --auth-login admin:admin123 --auth-surface --report .\reports\auth

    第四步，按结果决定要不要碰弱口令（先确认锁定策略）：
    ruoyi-scan -l http://target:8080/ --pass-level top100

    第五步，出交付报告（7 格式一次到位）：
    ruoyi-scan -u http://target:8080/ --auth-login admin:admin123 --components --report .\reports\final

    说明：
    - 第三步的 --auth-surface 会盘点登录态可见接口并做越权矩阵，比单纯跑 POC 更容易出成果。
    - 有高低权两个账号时加 --surface-account 低权账号:密码，垂直越权才有对比基准。

3.3 场景 C：等保测评 / 合规验收，要的是报告
-------------------------------------------------------------------------------
    目标：条款对应清楚，报告能直接进交付物。

    ruoyi-scan -u http://target:8080/ --template dengbao --report .\reports\dengbao

    需要 OWASP 口径时：
    ruoyi-scan -u http://target:8080/ --template compliance --report .\reports\owasp

    --template dengbao 只跑带等保 2.0 映射的插件，报告里的「合规映射」章节会列出
    条款号；--template compliance 同理对应 OWASP Top 10。

    交付建议：
    - 主报告给 HTML（人看），机器存档给 JSON（复测要用），盖章版用 PDF。
    - UNKNOWN 要单独说明原因，不要混进「不存在」，否则测评方会认为你漏测。

3.4 场景 D：上线前卡点（CI / DevSecOps）
-------------------------------------------------------------------------------
    目标：有高危就不许发布，且结果能进代码扫描面板。

    ruoyi-scan -u http://staging:8080/ --ci --severity-threshold high --report .\reports\ci --report-format sarif

    - --ci 模式下发现 >= high 的 CONFIRMED 会以非 0 退出，流水线自动失败。
    - report.sarif 可直接被 GitHub Code Scanning / GitLab 消费。
    - 建议只对测试环境跑，不要在发布流水线里打生产。

    生成流水线模板：
    ruoyi-scan --ci-init github

3.5 场景 E：应急，怀疑已经被打
-------------------------------------------------------------------------------
    目标：快速确认「某个具体漏洞」是否存在，而不是全面体检。

    先缩小范围，只跑相关插件（插件名见 ruoyi-scan-plugins.txt）：
    ruoyi-scan -p http://target:8080/ --report .\reports\ir

    需要确认利用链是否可达时：
    ruoyi-scan --chain-list
    ruoyi-scan --chain ruoyi_sql_to_rce -u http://target:8080/

    注意：
    - 利用链只做「可验证到哪一步」的验证，不落地 webshell、不拖库。
    - 应急场景优先保留现场：报告 JSON 里带 URL、时间、证据，先存档再复测。
    - 怀疑有 WAF 拦截导致测不出，用 --bypass-waf on 再跑一次，仍 UNKNOWN 就人工上。

3.6 场景 F：整改后复测，要证明修好了
-------------------------------------------------------------------------------
    思路：留基线 → 整改 → 复测 → 出差异报告。

    第一次（整改前）：
    ruoyi-scan -u http://target:8080/ --report .\reports\baseline

    整改完成后：
    ruoyi-scan -u http://target:8080/ --report .\reports\retest --remediation .\reports\baseline\report.json

    只对比两份已有报告（不重新扫描）：
    ruoyi-scan --diff-only .\reports\baseline\report.json .\reports\retest\report.json

    复测报告会标出：已修复 / 仍存在 / 新增。给甲方看的核心就是这一页。


===============================================================================
 4. 确认是若依之后：怎么打得更深
===============================================================================

4.1 先判版本，版本决定哪些洞存在
-------------------------------------------------------------------------------
    工具会从登录页版权年份、静态资源、接口特征推断版本，报告顶层有 fingerprint。
    已知的版本差异（内置矩阵实测）：

    4.6.2 及以下  定时任务 invokeTarget 白名单缺失；两个越权 CVE 存在
    4.7.8 / 4.8.0 两个越权 CVE 存在（CVE-2025-46174 / CVE-2025-70986）
    4.8.2 及以上  上述问题已修复，跑出来多为 SAFE

    这意味着：
    - 打出 4.8.2+ 的 SAFE 是正常结论，不是工具坏了。
    - 打出 4.6.2 的定时任务 RCE 相关结论，要重点看证据。

4.2 登录态是分水岭
-------------------------------------------------------------------------------
    未登录能测的：未授权接口、默认口令、部分文件读取、源码/备份泄露
    必须登录才准的：越权、后台功能点、定时任务、代码生成器

    优先用 --auth-login 自动登录（内置验证码识别与重试）。
    验证码识别失败时，浏览器登录后复制 Cookie：
    ruoyi-scan -u http://target:8080/ --auth cookie=JSESSIONID=xxxx

4.3 变体识别：别把 Plus 的洞套到单体上
-------------------------------------------------------------------------------
    工具会识别 5 种变体，并按变体路由插件：
    Vue3 / App / Plus / Cloud-Plus / Magic

    典型误判：把 Plus 专属接口（如 /plus/...）的结论套到标准单体上。
    如果报告里出现「某 Plus 漏洞 CONFIRMED」但目标明显是标准版，先复核指纹与证据。

4.4 未授权接口的三条高频路径（人工也要看）
-------------------------------------------------------------------------------
    - /actuator/*（env、heapdump、jolokia）：Spring Boot 暴露面
    - /druid/*：监控台未授权或弱口令
    - /swagger-ui / /v2/api-docs：接口文档泄露，直接拿到全量 API

    工具会覆盖这些，但人工访问一遍能发现「工具没覆盖的自定义接口」。

4.5 定时任务链（4.6.2 及以下）
-------------------------------------------------------------------------------
    判定逻辑是「写 invokeTarget → 回读确认生效 → 还原」，不会真的执行命令。
    看到 CONFIRMED 说明编辑接口可达且白名单缺失，利用价值需要结合版本与账号权限判断。

4.6 文件读取 / 上传的验证姿势
-------------------------------------------------------------------------------
    文件读取：看证据里的回显内容（是否有 root:x:0:0 这类真实文件特征）
    文件上传：工具只上传探针并验证可访问性，不传可执行木马
    报告里如果只有状态码没有回显，按 UNKNOWN 处理，别直接写进交付报告

4.7 组件 CVE
-------------------------------------------------------------------------------
    ruoyi-scan -p http://target:8080/ --components

    会比对 fastjson / Shiro / Nacos / Log4j 等 20 个组件的版本区间。
    组件版本常常比框架漏洞更致命，尤其是 fastjson 与 Shiro。


===============================================================================
 5. 实战小技巧（20 条）
===============================================================================

 [1] 第一次接触目标先 -p：10 秒内能判断是不是若依，别直接 -u 打草惊蛇。
 [2] -m 之前想清楚：目录扫描请求量大且特征明显，容易被 WAF 拉黑。
 [3] --time-budget 是你的安全绳：批量扫描一定加，避免个别目标拖死整批。
 [4] 生产环境 --threads 5 --rate 10 起步，观察对方响应再决定是否加速。
 [5] 弱口令按 top100 → top1000 → full 递进，先确认账号锁定策略。
 [6] 自动登录失败先看是不是验证码：换 --auth cookie= 手工注入更稳。
 [7] 只要拿到账号，务必加 --auth-surface：越权往往比 POC 更容易出成果。
 [8] 有高低权两个账号，用 --surface-account 做对比，否则测不出垂直越权。
 [9] --components 必开：组件 CVE 经常是整条链里最值钱的那个。
 [10] 报告目录按目标分开：report.<ext> 是固定名，同目录重扫会覆盖。
 [11] 批量扫描会自动按目标建子目录，别自己再套一层。
 [12] 看到 UNKNOWN 先看原因：超时、WAF、验证码、登录墙，处理方式完全不同。
 [13] 目标在非标准端口或带 context-path 时，URL 要写全：http://ip:8081/ruoyi/
 [14] 内网自签名证书不用管（默认不校验证书）；公网目标可加 --verify-tls。
 [15] 想复用社区规则：--nuclei 目录，配合 --nuclei-tags / --nuclei-severity 过滤。
 [16] 团队协作别各自跑：--serve 起 Web 控制台，任务队列共享，报告统一落盘。
 [17] 复测一定要带 --remediation，靠人眼对比两份 JSON 迟早出错。
 [18] CI 里只跑测试环境，且用 --severity-threshold high，别让中低危阻塞发布。
 [19] 报告先出 JSON 存档，再出 HTML/PDF 交付；JSON 是复测与取证的底稿。
 [20] 每次扫描记录：时间、源 IP、参数、目标、结论。出事时这是你的免责证据。


===============================================================================
 6. 怎么读结果：三态不是装饰
===============================================================================

6.1 CONFIRMED：拿到证据才算
-------------------------------------------------------------------------------
    报告每条 CONFIRMED 都带证据（状态码 + 命中内容 / 回显片段）。
    交付前自检三问：
    - 证据能不能复现？（报告里有复现命令）
    - 证据是不是 payload 自己的回显？（差分判定已排除大部分，但人工要扫一眼）
    - 影响面写清楚了吗？（未授权 / 需登录 / 需管理员）

6.2 SAFE：可以信，但要看清前提
-------------------------------------------------------------------------------
    SAFE = 在当前版本、当前配置、当前网络条件下验证过不存在。
    以下情况 SAFE 不成立，应视为 UNKNOWN：
    - 目标在 WAF 后面，请求被拦截但返回了正常页
    - 需要登录才能访问的接口，未登录时返回登录页
    - 目标响应被 CDN 缓存

6.3 UNKNOWN：绝不等于安全
-------------------------------------------------------------------------------
    四种常见成因与对策：
    网络不通 / 超时        → 检查连通性，调大 --timeout，重跑
    WAF 拦截（403/429）    → --bypass-waf on；仍不行记录为「被测方 WAF 阻断」
    验证码 / 登录墙        → --auth-login 或 --auth cookie= 补登录态
    接口返回 401/403       → 说明有鉴权，属于「没权限测」，不是「不存在」

    写报告时把 UNKNOWN 单列一节，注明原因与建议复核方式，这是专业度的体现。


===============================================================================
 7. 合规与边界（不是免责声明，是操作规范）
===============================================================================

7.1 授权要写到什么程度
-------------------------------------------------------------------------------
    至少包含：目标域名/IP/端口、允许的测试手法、时间窗、是否允许弱口令爆破、
    是否允许登录后测试、甲方应急联系人。
    口头同意不算。邮件/工单/合同附件才算。

7.2 扫描节奏与业务影响
-------------------------------------------------------------------------------
    - 避开业务高峰、批处理窗口、发版窗口
    - 爆破类操作先确认账号锁定策略，避免锁死管理员
    - 大流量扫描前告知值守人员，避免被当成攻击导致封 IP / 关站
    - 一旦对方业务出现异常，立即停扫并保留现场

7.3 证据与数据处置
-------------------------------------------------------------------------------
    - 只取最小证据：证明漏洞存在即可，不下载业务数据、不导出用户表
    - 证据落盘加密，交付后按约定删除
    - 报告里的手机号、身份证、密钥一律打码

7.4 报告口径
-------------------------------------------------------------------------------
    - CONFIRMED 才写「存在」，UNKNOWN 写「无法判定」，SAFE 写「已验证不存在」
    - 不夸大：验证到「可读取文件」就写文件读取，不要写成 RCE
    - 修复建议给到可执行粒度（升级版本号 / 配置项 / 代码改法）

7.5 法律红线
-------------------------------------------------------------------------------
    《网络安全法》第二十七条、《刑法》第二百八十五条、第二百八十六条，
    《数据安全法》相关条款。未授权扫描、越权访问、数据窃取都可能构成犯罪。
    工具只提供验证能力，使用者的授权与边界由使用者自己负责。


===============================================================================
 8. 常见坑（按现象查）
===============================================================================

    现象：全是 UNKNOWN，一个 CONFIRMED 都没有
    排查：目标是否可达 → 是否 WAF → 是否需要登录 → 是否根本不是若依

    现象：目录扫描报了大量「存在」，但浏览器打开是 404
    原因：SPA / nginx try_files 对任意路径返回 200；v1.5.2 已内置软 404 基线，
          自建改版站点仍建议人工抽查两条

    现象：自动登录一直失败
    原因：验证码识别失败 / 账号锁定 / 登录接口被改
    处理：浏览器手工登录后 --auth cookie=；确认账号未被锁

    现象：明明 4.8.3 还报 4.8.0 的洞
    处理：看报告指纹置信度；低置信度时用 --cms ruoyi 强制路由后复核证据

    现象：扫到一半目标全 403
    原因：WAF 拉黑
    处理：停扫，换 IP / 降速，联系对方加白；不要硬绕

    现象：报告被覆盖了
    原因：report.<ext> 固定名
    处理：每次 --report 换目录

    现象：--report 写了但没生成文件
    处理：确认路径可写；容器内注意挂载卷；PDF/DOCX/XLSX 需要 [report] 依赖
