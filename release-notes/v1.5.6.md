# Ruoyi-Scan v1.5.6 — 口径正确性版

v1.5.5 解决的是「该报的能报」：54 个插件里 46 个有 CONFIRMED 产出。
本版不追数字，解决的是**「报出来的能不能直接信、能不能直接用于交付」**。

盲测 v4 复测：**48/54** 插件有 CONFIRMED（v1.5.5 为 46），**v3 产出 0 丢失，B 类误报 0**。

---

## 一、能力增强

### 自定义 context-path 识别

此前候选前缀表写死 5 个（`/prod-api` `/dev-api` `/api` `/jeecg-boot` `/jeecg`）。
二开站点把后端挂在 `/portal` 这类自定义前缀下时，一个判据都对不上 → 路径类插件整类探错基准。

现在从**已经在拿的响应**里读线索，不发额外请求：

- `Set-Cookie` 的 `Path=`（后端自己声明的 cookie 作用域，最可靠）
- 302 的 `Location`（**绝对 URL 形态也认**——nginx `return 302 http://$host/portal/` 就是这种）
- JS/HTML 里的 `baseURL` 赋值

抽出的候选**仍要过验证码判据**才被采纳，判定不放松。
另加 `--base-path /portal` 显式指定，优先级最高（运维知道真实前缀时不该赌探测）。

### RuoYi 4.x 图片型验证码判据

4.x 单机版/Thymeleaf 版的验证码是 `/captcha/captchaImage` 返回 **`image/jpeg` 而非 JSON**，
此前完全认不出。现在两种形态都认。

判据同时校验 `Content-Type` **和最小字节数（512）**——必须带 `type=char`：
无参时返回 200 + **0 字节**（`BufferedImage` 为 null、异常被框架吞），
只看 Content-Type 会把「探测失败」当成「接口存在」。

### `--redis-port`（Redis 端口可配）

Redis 未授权插件此前把 6379 写死。现场几乎不用默认端口（云厂商安全组优先封 6379），
靶场也常挪到高端口；写死端口时这些目标恒判「连接失败」，而插件本身完全有能力在任意端口验证。

```bash
ruoyi-scan -u http://target:8080/ --redis-port 16379
```

连不上的证据里现在带上实际探测端口与开关名，用户能区分「没开 Redis」和「端口传错」。

### Windows `win.ini` 文件读取

盲测 v3 记录两个「任意文件读取」零产出，归因是「Windows 靶场无法提供 `/etc/passwd` 型证据」。
核实后发现不是靶场问题——是判据只有 Linux 特征，外加一条 `[boot loader]`
（那是 **boot.ini**，XP 引导配置，Win10/11 早已不存在，是另一个文件）。
`file_read` 的 `reproduce` 里早就写了 win.ini 的 curl，判据却不支持：文档承诺了、代码没实现。

现在 `file_read` / `file_read_path` 双载荷：Linux 读 `/etc/passwd`、Windows 读 `win.ini`，
任一命中即 CONFIRMED。判据认 `for 16-bit app support` 注释行（win.ini 独有）
或 ≥3 个特征段头；单段不判（`[files]`/`[Mail]` 在任意 INI/HTML 里都可能出现）。

## 二、口径修正（本版重点）

### 归属判定：站点漏洞 vs 宿主级资产

中间件插件（Redis/MinIO/RocketMQ）探的是**目标主机的独立端口**，不是站点路径。
多站点共用宿主时，同一个宿主漏洞会在**每份站点报告里各报一次**——
盲测 v4 里 Redis 出现在 **44 份报告**里，而它只是 **1 个主机暴露**。

新增归属判定，按「探测坐标的端口轴」区分：

- 与目标同源同端口 → **站点级**（站点自身的漏洞）
- 另一个端口 / 另一台主机 → **宿主级**（资产无法证明属于该站点）

**只标注不降级**：端口确实无认证，CONFIRMED 不变；归属是三态之外的正交维度。
单目标报告有归属列 + 横幅，批量报告概览表单列「其中宿主级」并说明「同一主机上的多个站点
会各自报出同一批宿主发现，按主机去重看待」。

### 端点不存在不再冒充「确认安全」

RuoYi-Vue-Plus **5.6.2 的定时任务已迁到 SnailJob**（独立调度中心），
源码里根本没有 `SysJobController`，`/monitor/job/**` 返回 `HTTP 200 + code=404`。

`plus_job_unauth` 此前把这种情况判 SAFE——等于用「地址错了」冒充「系统是安全的」。
三态纪律里 SAFE = 测过了、确认不存在；端点不存在时没有可测的东西，应当 UNKNOWN。

改为按若依 `AjaxResult` 业务码判定（**若依对未知路由返 HTTP 200，看状态码会漏**）。

### 认证链不再假设登录入口是 `{base}/login`

二开站点常改登录路径（D1 是 `/portal/auth/signin`）。硬编码假设导致
`--auth-login` 恒 exit 4、依赖会话的插件全部拿不到结论。

改为从登录页的 **form action** 读真实入口，只认同源 + `method=post` + 含 `password`
输入框的表单（否则搜索框/筛选器都会被当成登录入口）。

### Shiro 插件不再虚报 high 级 RCE

此前挂 `CVE-2016-4437` + `severity=high` + 名称带「反序列化」，
但它只做指纹识别、**设计上永不 CONFIRMED**。报告里出现「high 级 Shiro 反序列化 RCE」
会让读者以为扫描器确认了可利用性。

改为 `cve=N/A`、`severity=low`、`category=recon`、名称去掉「反序列化」。
保留手工验证步骤在 `reproduce` 里，只是扫描器不再替它下结论。

## 三、盲测 v4 结果

| 指标 | 盲测 v3（v1.5.5） | 盲测 v4（v1.5.6） |
|---|---|---|
| 有 CONFIRMED 产出的插件 | 46/54 | **48/54** |
| 零产出插件 | 8 | **6** |
| v3 已有产出在 v4 丢失 | — | **0** |
| B 类硬误报 | 0 | **0** |

新增 2 项：Redis 未授权访问（端口可配）、备份文件泄露（靶场补齐）。

**剩余 6 个零产出全部是已识别边界**，无一为未知漏报：

- 目录扫描 / HTTP 方法探测：recon 类，设计上不产 CONFIRMED
- Shiro 框架指纹：已收口为 `category=recon`，只到 SAFE/UNKNOWN
- 任意文件读取 ×2：判据（含 win.ini）已就绪，缺的是**未授权可读**的靶场读点
- RuoYi-Plus 定时任务：5.6.2 已改用 SnailJob，该端点不存在

详见 [盲测 v4 报告](https://github.com/xiabai2008/Ruoyi-Scan/blob/main/docs/blind_test_report_v4.md)。

## 四、升级提示

- 报告结构新增字段：`risk_distribution.host_level`、`host_level_count`、
  每条结果 `extra.attribution`。消费报告 JSON 的脚本可按需读取（旧字段不变）。
- 单目标 HTML/CSV 新增「归属」列（11 → 12 列）。
- `--redis-port`、`--base-path` 可写进 YAML 配置（`redis_port:` / `base_path:`）。
